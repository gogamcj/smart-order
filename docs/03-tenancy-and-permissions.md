# 업체별 권한과 데이터 격리 구조

## 1. 3중 방어

| 계층 | 무엇을 막나 | 구현 |
|---|---|---|
| 1. API 가드 | 로그인·역할·업체 멤버십·자원 소유권 | NestJS Guard + 데코레이터 `@Roles('order_staff')`, 모든 조회 조건에 세션의 tenantId 사용 (2단계) |
| 2. PostgreSQL RLS | API 코드가 업체 조건을 빠뜨려도 다른 업체 행이 보이지 않음 | `0006_rls_and_grants.sql` (구현·테스트 완료) |
| 3. 제약조건 | 업체가 다른 부모를 참조하는 데이터 자체를 만들 수 없음 | `(id, tenant_id)` 복합 외래 키 (구현·테스트 완료) |

### 요청 처리 방식

```ts
// 2단계에서 구현할 요청 컨텍스트 (개념 코드)
await db.transaction(async (tx) => {
  await tx.execute(sql`SET LOCAL ROLE qr_app`);           // 또는 qr_app 멤버 계정으로 접속
  await tx.execute(sql`SELECT set_config('app.tenant_id', ${session.tenantId}, true),
                              set_config('app.user_id', ${session.userId}, true),
                              set_config('app.actor_kind', ${session.actorKind}, true)`);
  return handler(tx);
});
```

- `tenantId` 는 **세션에서만** 가져옵니다. 직원은 로그인 시 선택한 업체(멤버십 검증), 고객은 QR 검증 결과입니다. URL·본문의 업체 ID 는 사용하지 않습니다.
- `set_config(..., true)` 는 트랜잭션 범위라 커넥션 풀(PgBouncer 트랜잭션 모드 포함)에서도 다른 요청으로 새지 않습니다.
- 컨텍스트가 없으면 `app.current_tenant_id()` 가 NULL 이 되어 **아무 행도 보이지 않습니다**(fail closed).

### DB 역할

| 역할 | 사용처 | 범위 |
|---|---|---|
| `qr_app` | 일반 API (고객·업체 직원) | RLS 적용 |
| `qr_system` | 결제 확정, PG 웹훅, 대사·만료·알림 워커, 최고 관리자 모듈, 로그인 처리 | 정책상 전체 접근. 코드 리뷰 대상 모듈을 제한 |
| 소유자 | 마이그레이션 전용 | 애플리케이션에서 사용 금지 |

## 2. 업체 상태와 접근 제어

| 업체 상태 | 업체 관리자 로그인 | 메뉴·테이블 설정 | 고객 QR 접속 | 주문 생성 |
|---|---|---|---|---|
| `pending` (승인 대기) | O | O (준비 가능) | X | X (DB 트리거로 차단) |
| `active` | O | O | O | O (업체가 `accepting_orders=false` 면 X) |
| `rejected` | 신청 정보 확인만 | X | X | X |
| `suspended` (정지) | 조회 전용 | X | X | X |
| `closed` (탈퇴) | X | X | X | X |

DB 에서 강제되는 부분(테스트 완료): 승인 대기·정지 업체 주문 생성 차단, 정지 업체 QR 해석 차단, 직원이 자기 업체 승인 상태를 바꾸는 것 차단(컬럼 권한). 나머지는 2단계 API 가드에서 구현합니다.

### 최고 관리자의 개인정보 제한

- 최고 관리자 화면 API 는 고객 식별 정보를 반환하지 않습니다(주문 번호·금액·상태·업체만). 연락처 복호화 키는 알림 워커에만 주입합니다.
- 장애 대응으로 특정 주문의 고객 정보를 봐야 하면 사유 입력 → 감사 로그 기록 후 해당 건만 조회(5단계).
- 최고 관리자 계정은 2단계 인증(TOTP) 필수(5단계).
